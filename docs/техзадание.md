# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: ИИ-консультант MTS EnergyTool (финальная версия v3.0)

---

## 1. Общие сведения и ограничения

**Цель:** Разработать ИИ-консультанта, который ведёт B2B-клиента от описания проблемы до сформированной заявки менеджеру, используя RAG по базе знаний MTS EnergyTool.

**Решение состоит из двух частей:**
- **Этап 1 (headless):** скрипт `solution.py` для автоматической оценки LLM-судьёй.
- **Этап 2 (финал):** веб-приложение с чатом, Debug-панелью и сбором лида.

### 1.1. Жёсткие ограничения платформы (Этап 1)

| Ограничение | Значение | Источник |
| :--- | :--- | :--- |
| **Структура ZIP** | Все `.py`-модули — **в корне архива, без внешней папки-обёртки**. Вложенные папки запрещены. | `Технический регламент`, стр. 2, п. 4 |
| **Точка входа** | `solution.py` — обязательная точка входа, самостоятельно читает вопросы, обращается к модели и создаёт `submission.csv`. | `Технический регламент`, стр. 2, п. 4 |

| **Формат CSV** | UTF-8, ровно две колонки `id,answer`, стандартное CSV-экранирование (`csv.QUOTE_ALL`). **Переводы строк НЕ удаляются.** | `Технический регламент`, стр. 2, п. 3 |

| **Запрет `pip install`** | Вызовы `pip install` из `solution.py` запрещены. Все зависимости — в `requirements.txt`. | `Технический регламент`, стр. 2, п. 4 |
| **Промежуточные файлы** | Можно создавать в рабочем каталоге или `/tmp`. | `Технический регламент`, стр. 2, п. 4 |
| **Безопасность** | Запрещены хардкод-ключи; только тестовые ПДн. | `МТС_кейс.pdf`, стр. 10, п. 8, 9 |

## 2. Стек технологий

### 2.1. Этап 1: `solution.py` (один Docker-контейнер, без внешних сервисов)

| Подзадача | Технология | Обоснование |
| :--- | :--- | :--- |
| HTTP-клиент | `httpx` (синхронный `Client` в потоках) | Асинхронность не нужна — `ThreadPoolExecutor` достаточно, как в `sample_submission`. |
| Парсинг KB | `zipfile` + стандартная библиотека | Минимум зависимостей, быстро. |
| Чанкинг | Кастомный парсер по заголовкам `#`, `##` с сохранением таблиц | Таблицы не должны рваться. |
| Векторный поиск | `FAISS` (CPU) или `numpy` (косинусное сходство in-memory) | KB маленькая, влезет в RAM. |
| Лексический поиск | `rank_bm25` (in-memory) | Точный поиск цифр и терминов. |
| Реранкер | HTTP-запрос к `/rerank` через локальный прокси | Опционально, через `RERANKER_MODEL`. |
| Хранение контекста | `dict` in-memory (в рамках одного тест-кейса) | Тест-кейсы независимы между собой. |
| CSV | `csv.writer` с `quoting=csv.QUOTE_ALL` | Стандартное экранирование по RFC 4180. |

### 2.2. Этап 2: Веб-приложение (финальная сдача, Docker Compose)

| Подзадача | Технология | Обоснование |
| :--- | :--- | :--- |
| Backend | `FastAPI` + `Uvicorn` | Асинхронность, `Pydantic` для DTO. |
| RAG-оркестрация | `LlamaIndex` | Гибридный поиск, реранкеры из коробки. |
| Векторная БД | `Qdrant` (Docker) | Фильтрация по метаданным, гибридный поиск. |
| БД сессий/лидов | `PostgreSQL` + `SQLAlchemy` + `Alembic` | Хранение истории, лидов, метаданных. |
| Frontend | `Next.js` + `TailwindCSS` + `shadcn/ui` | SSR, компонентный подход. |
| Инфраструктура | `Docker` + `docker-compose` | Одна команда запуска. |

## 3. Архитектура решения

### 3.1. Ключевое ограничение: плоская структура для Этапа 1

Согласно `Технический регламент`, стр. 2, п. 4:
> «Не размещайте необходимые для запуска модули во вложенных папках».

**Следствие:** Все `.py`-модули, импортируемые `solution.py`, лежат **в корне ZIP-архива**. Импорты — вида `import rag`, `import llm_client`, без префиксов папок. **Внешней папки-обёртки в ZIP быть не должно.**

### 3.2. Архитектурные принципы (для обеих частей)

1. **Ports & Adapters (Hexagonal Architecture):** LLM, Retriever, Repository описаны через `Protocol` (порты). Реализации — в адаптерах.
2. **Dependency Inversion:** Домен не зависит от инфраструктуры.
3. **Single Responsibility:** Один модуль — одна ответственность.
4. **Явные зависимости:** Всё через конструктор (DI), никаких глобальных синглтонов.
5. **Strategy Pattern:** Выбор retriever (BM25 / Vector / Hybrid) — через стратегию.
6. **State Machine / Dialog Manager:** Управление диалогом — отдельный модуль. Конкретная реализация (автомат, граф, LLM-агент) — на выбор команды.

### 3.3. Антипаттерны, которых избегаем

| Антипаттерн | Как избегаем |
| :--- | :--- |
| **Вложенные папки для Этапа 1** | Все `.py` — в корне ZIP. |
| **Внешняя папка-обёртка в ZIP** | Файлы лежат напрямую в корне архива. |
| **Бизнес-логика в адаптерах** | State machine и prompt-билдер — в домене. Адаптер LLM — только HTTP-запрос. |
| **God Object** | Разделение на `rag.py`, `llm_client.py`, `dialog.py`, `csv_processor.py`. |
| **Hardcoded configs** | Всё через `os.getenv` + класс `Settings`. |
| **Глобальный mutable state** | Отсутствует. Контекст передаётся явно. |
| **Удаление `\n` в CSV** | Используем `csv.writer(..., quoting=csv.QUOTE_ALL)`. |
| **Синхронные блокировки в async** | В Этапе 2 — `httpx.AsyncClient`. В Этапе 1 — `ThreadPoolExecutor`. |
| **Магические строки** | Enum для ролей, состояний, типов источников. |

## 5. Алгоритм работы системы

### 5.1. Этап 1: `solution.py`

```
1. Инициализация:
   - settings = Settings()  # читает os.getenv
   - data_dir = Path(settings.DATA_DIR or "data")
   - Поддержка альтернативных имён файлов:
     * questions.csv или train.csv
     * knowledge-base.zip или knowledge_base.zip или kb.zip
   - questions_path = find_file(data_dir, "questions.csv", "train.csv")
   - kb_path = find_file(data_dir, "knowledge-base.zip", "knowledge_base.zip", "kb.zip")

2. Загрузка KB в память (один раз):
   - Распаковка knowledge-base.zip в tempfile.mkdtemp() или /tmp/mts-kb/
   - Парсинг .md файлов с сохранением иерархии заголовков
   - Структурный чанкинг (таблицы не рвутся)
   - Построение in-memory индексов: FAISS (векторный) + BM25 (лексический)

3. Обработка вопросов (параллельно через ThreadPoolExecutor):
   Для каждого тест-кейса (id, question):
   
   a) Парсинг истории (если есть):
      - Если в question есть маркеры "Пользователь:" / "Ассистент:",
        извлечь их в список сообщений.
      - Последняя реплика пользователя — текущий запрос.
      - Пример парсинга:
        ```python
        def parse_history(question: str) -> tuple[list[dict], str]:
            lines = question.strip().split("\n")
            history = []
            current_query = []
            for line in lines:
                if line.startswith("Пользователь:"):
                    if current_query:
                        history.append({"role": "user", "content": " ".join(current_query)})
                        current_query = []
                    current_query.append(line[len("Пользователь:"):].strip())
                elif line.startswith("Ассистент:"):
                    if current_query:
                        history.append({"role": "user", "content": " ".join(current_query)})
                        current_query = []
                    history.append({"role": "assistant", "content": line[len("Ассистент:"):].strip()})
                else:
                    current_query.append(line.strip())
            if current_query:
                if history and history[-1]["role"] == "user":
                    history[-1]["content"] += " " + " ".join(current_query)
                else:
                    history.append({"role": "user", "content": " ".join(current_query)})
            last_query = history.pop()["content"] if history else question
            return history, last_query
        ```
   
   b) Retrieval:
      - HybridRetriever: объединение BM25 + Vector (RRF)
      - Top-K кандидатов (из TOP_K)
      - Реранкер (опционально, RERANKER_TOP_N)
   
   c) Формирование промпта:
      - system = prompts.SYSTEM_PROMPT
      - context = "\n".join(chunks)
      - history = [сообщения из тест-кейса]
      - messages = [system] + history + [user: текущий запрос + context]
   
   d) Вызов LLM:
      - POST {LLM_BASE_URL}/chat/completions
      - headers = {"Authorization": f"Bearer {LLM_API_KEY}"}
      - temperature = TEMPERATURE, max_tokens = MAX_TOKENS
      - Retry при 429/5xx (экспоненциальная задержка, максимум 2 попытки)
   
   e) Постобработка:
      - Если ответ пустой или ошибка → fallback:
        "Не могу ответить по доступным фрагментам базы знаний."
      - Обрезка до 10 000 символов (жёсткий лимит)
      - НЕ удалять \n (CSV-экранирование сделает это корректно)

4. Запись submission.csv:
   - Путь: Path.cwd() / "submission.csv" (рабочий каталог)
   - encoding = "utf-8"
   - csv.writer(f, quoting=csv.QUOTE_ALL, lineterminator='\n')
   - writer.writerow(["id", "answer"])
   - writer.writerows([(id, answer), ...])
   - Проверка: ID не повторяются, нет пустых ответов
```

### 5.2. Этап 2: Веб-приложение

```
1. Пользователь пишет в чат → POST /api/chat
2. FastAPI → ProcessMessageUseCase:
   - SessionRepository.get_history(session_id)
   - DialogManager.next_state(history, query)
   - RetrievalPort.retrieve(query) → Hybrid + Rerank
   - PromptBuilder.build(state, chunks, history)
   - LLMPort.generate(messages)
   - PostProcessor.enforce_limits(answer)  # ≤ 10 000 символов
   - SessionRepository.append_message(...)
3. Ответ: {answer, sources, latency}
4. Debug-панель: отображает sources (файл + excerpt) и latency.
5. Сбор лида:
   - Когда пользователь готов → бот запрашивает ФИО, телефон, компанию.
   - Валидация: regex для телефона, непустые ФИО и компания.
   - GenerateLeadSummaryUseCase: отдельный вызов LLM для резюме.
   - LeadRepository.save(lead)
6. Кнопка «Новый диалог» → POST /api/reset → новый session_id.
   Старая сессия сохраняется в БД.
```

## 7. Поэтапная реализация с тестами

### Этап 1. In-Memory RAG и `solution.py`

**Задачи:**
1. `settings.py`: чтение всех переменных окружения с валидацией.
2. `rag.py`:
   - Парсинг `knowledge-base.zip` (только `.md` и `.txt`).
   - Структурный чанкинг по заголовкам `#`, `##` с сохранением таблиц.
   - Построение FAISS-индекса (эмбеддинги через `/embeddings`).
   - Построение BM25-индекса (`rank_bm25`).
   - `HybridRetriever`: объединение через RRF (Reciprocal Rank Fusion).
3. `llm_client.py`:
   - `LLMClient` с методами `generate()`, `embed()`, `rerank()`.
   - Retry при 429/5xx (экспоненциальная задержка, максимум 2 попытки).
   - Fallback при ошибке: `"Не могу ответить по доступным фрагментам базы знаний."`
4. `prompts.py`:
   - `SYSTEM_PROMPT`: роль консультанта, запрет галлюцинаций, Guardrails.
   - `FALLBACK_ANSWER`: шаблон для случая отсутствия ответа.
5. `dialog.py`:
   - `parse_history(question: str) -> tuple[list[dict], str]`: извлечение истории из тест-кейса.
   - Если в `question` есть маркеры `Пользователь:` / `Ассистент:`, разобрать их.
   - Последняя реплика пользователя — текущий запрос.
6. `csv_processor.py`:
   - `read_questions(path) -> list[tuple[str, str]]`: чтение `questions.csv`.
   - `write_submission(path, answers)`: запись через `csv.writer(..., quoting=csv.QUOTE_ALL)`.
   - Путь к `submission.csv` — `Path.cwd() / "submission.csv"`.
7. `solution.py`:
   - Тонкая обёртка: инициализация → загрузка KB → обработка вопросов → запись CSV.
   - Параллелизм через `ThreadPoolExecutor(max_workers=MAX_WORKERS)`.
   - Поддержка альтернативных имён файлов (`train.csv`, `knowledge_base.zip`, `kb.zip`).

**Тесты:**
- `test_rag.py`:
  - Запрос «порог оптового рынка» → чанки из `21-orem.md` в Top-3.
  - Таблицы не разрезаны (проверка наличия шапки в каждом чанке).
- `test_dialog.py`:
  - Парсинг истории из тест-кейса с маркерами `Пользователь:` / `Ассистент:`.
  - Пустая история → список сообщений пуст.
- `test_csv_processor.py`:
  - Запись и чтение `submission.csv` с переносами строк в ответах.
  - Проверка, что CSV валиден (нет поломанных строк).
  - Проверка, что файл создан в cwd.
- `test_solution.py`:
  - Smoke-тест: запуск на `demo_questions.csv` с моками LLM.
  - Проверка структуры `submission.csv`: колонки `id`, `answer`, все ID на месте.
  - Проверка, что ID не повторяются.

### Этап 2. Домен и веб-интерфейс

**Задачи:**

## 8. Чек-лист сдачи

### Этап 1 (headless)
- [ ] `solution.py` и все `.py`-модули лежат **в корне ZIP** (без вложенных папок, без внешней папки-обёртки).
- [ ] `solution.py` читает `DATA_DIR` из `os.getenv` (по умолчанию `data`).
- [ ] Поддерживаются альтернативные имена файлов (`train.csv`, `knowledge_base.zip`, `kb.zip`).
- [ ] Используются только in-memory решения (FAISS, BM25, `dict`).
- [ ] `submission.csv` создаётся в **рабочем каталоге (cwd)**, а не в `DATA_DIR`.
- [ ] `submission.csv` создаётся через `csv.writer(..., quoting=csv.QUOTE_ALL)` с `encoding="utf-8"`.
- [ ] Переводы строк в ответах **не удаляются** (корректное CSV-экранирование).
- [ ] В `submission.csv` ровно две колонки: `id`, `answer`.
- [ ] ID не повторяются.
- [ ] Ответы ограничены 10 000 символов (жёсткий лимит).
- [ ] Все переменные окружения из раздела 6 поддерживаются.
- [ ] Fallback при ошибке LLM: `"Не могу ответить по доступным фрагментам базы знаний."`
- [ ] История диалога парсится из `question` (маркеры `Пользователь:` / `Ассистент:`).
- [ ] Тест-кейсы независимы: состояние между ID не переносится.
- [ ] Промежуточные файлы (распаковка KB) создаются в `/tmp` или cwd.
- [ ] Запрещены вызовы `pip install` из `solution.py`.
- [ ] `PYTHONPATH` обрабатывается Python автоматически (вручную не обрабатывается).

### Этап 2 (финал)
- [ ] Веб-приложение поднимается одной командой `docker compose up`.
- [ ] UI: чат, сброс контекста, Debug-панель (источники + latency).
- [ ] Сбор лида: ФИО + телефон + компания + резюме.
- [ ] История всех сессий (включая без лида) сохраняется в БД.
- [ ] Guardrails запрещают выдумывание цен и фактов.
- [ ] `README.md` с одной командой запуска и описанием архитектуры.
- [ ] `.env.example` без ключей.
- [ ] `requirements.txt` (backend) и `package-lock.json` (frontend) с зафиксированными версиями.
